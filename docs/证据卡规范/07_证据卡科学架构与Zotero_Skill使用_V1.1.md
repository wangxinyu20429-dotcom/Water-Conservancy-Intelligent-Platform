## 二、证据卡的最小成立条件

一张卡只有同时具备下列内容，才可能进入科研判断：

1. 一个明确的当前问题和它会影响的决定；
2. 唯一来源身份、准确版本、真实阅读范围；
3. 对该类型证据生成机制的还原；
4. 至少一个 Cxx 原子声明块；
5. 声明的直接来源、精确范围、效应或阈值、不确定性和定位；
6. 允许的推断类型；
7. “直接支持”和“不能支持”；
8. 会改变结论的有效性威胁、冲突或失败情景；
9. 明确用途结论与受影响对象；
10. 补读三门判定、最小路径和停止条件。

卡片可以很短，但缺少其中任一承重环节时，不能用篇幅或流畅语言补足。

## 三、Cxx 原子声明怎么写

Cxx 是后续主题、问题、创新候选和工程决策的最小引用单位。一个 Cxx 只能写一个可被核对的命题。

合格写法必须回答：

- 原文直接报告了什么；
- 事实由哪组数据、试验、统计表、工程记录、条款、数据组件或代码运行产生；
- 对象、流域、时期、尺度、独立单位和比较条件是什么；
- 数值、单位、分母、效应量、区间或阈值是什么；
- 在哪个版本、页码、章节、图表、条款、文件或 commit；
- 它只允许哪一种推断；
- 它明确支持什么，又明确不能支持什么；
- 作者／发布方怎样解释，本方怎样判断；
- 是否有冲突、共享上游来源或尚未核到的决定性缺口。

快速判断层最多突出三项 Cxx。增加 Cxx 必须因为它会改变当前判断，不能为了显得全面。

## 四、用途结论

不用总分和笼统“可信度”。每个关键声明及整卡从下列状态中选择，并写出理由：

- 可直接使用；
- 限条件使用；
- 仅作线索；
- 暂不可用；
- 与当前问题无关。

“限条件使用”不是次等证据，而是把适用条件和外推边界一起交付。“与当前问题无关”也不代表来源质量差。

## 五、Zotero 到 Obsidian 的实际步骤

1. 在 Zotero 中锁定指定条目，核对题名、作者、年份和稳定标识。
2. 先在 Obsidian 查找是否已有同一来源，已有就更新原卡。
3. 说清当前研究问题、预定决定和输出目录，再调用 hydrology-evidence-cards。
4. Skill 只读 Zotero 本地接口，读取条目、附件清单和可用全文索引。
5. 按来源的主要证据角色选择一张模板；Zotero itemType 只作线索。
6. 先锁身份、版本和阅读覆盖，再还原证据生成机制。
7. 只为决定性结论建立 Cxx；每项回到直接来源核查。
8. 主动查负结果、失效条件、内部冲突、版本漂移和外推差距。
9. 给出用途结论；三门不全满足时不展开附件、代码和额外来源。
10. 运行结构校验后人工重开每个 Cxx 的定位。结构 PASS 不表示科学正确。
11. Git 只提交 Markdown、允许共享的链接和 Skill；PDF、Zotero 数据库、凭据、受限项目材料和大数据留在原系统。
12. 通过维护分支和 Pull Request 更新 GitHub；Obsidian 使用同一仓库副本，不另建第二套证据卡。

## 七、当前状态和下一项真实验收

V1.1 完成的是架构重构、八类独立模板和结构检查器。它没有用文件数量证明科研质量。

下一步应使用真实材料形成样本：

1. 一篇结果结构复杂的原创水利研究；
2. 一份有明确口径与修订记录的调查或监测报告；
3. 一份有版本束和质量说明的数据产品；
4. 一个与论文有版本关系的软件或模型制品。

每个样本记录真正难填、误读、遗漏和无效字段。样本导致规则修改后，该样本转为修订样本；新版本另选未参与形成的材料独立验收。
